# 적중 이펙트 설계 (v2 3번)

작성 2026-11-17. 대상 문서: `docs/V2.md` §1 3번 "적중 이펙트" (연출 범위 **[미정]** → 이 문서로 확정).

> **수정 (2026-11-17, 크기 조정):** 구현 후 사용자 요청으로 크기를 바꿨다. 단조는 **원 바깥으로만 퍼지는 도넛형**(판정 원을 가리지 않음), 연마는 **흠집 크기 정도**(도넛 아님). 판정별 차이는 한 프리팹의 배율이 아니라 **판정별 프리팹 3개**로 낸다. 아래 본문은 수정 내용을 반영했다. 계획: [plans/2026-11-17-hit-effects-size.md](../plans/2026-11-17-hit-effects-size.md). 아래 "UI 정렬 레이어"도 구현 후 추가된 내용이다.

## 의도

리듬게임식 미니게임의 손맛을 판정 순간의 시각 연출로 보강한다. (Roadmap 리스크: "리듬게임식 손맛은 판정 정밀도, 입력 지연 대응, 적중 사운드(v1)와 이펙트(v2)에 크게 의존한다.") 지금 시각 피드백은 색 변화뿐이다.

## 목표 (사용자 결정)

- **대상은 단조와 연마 두 미니게임.** 가열·열처리는 이번 범위가 아니다.
- **단조:** 원이 판정될 때 그 원 자리에서 **빛나는 이펙트**가 터진다. **원 바깥으로만 퍼지는 도넛형**이며 **판정 원(안쪽 원)은 가리지 않는다.** 퍼지는 정도는 판정별로 다르다.
  | 경우 | 이펙트 |
  |---|---|
  | Perfect | 가장 멀리 퍼짐 |
  | Good | 중간 |
  | 눌렀지만 Miss (타이밍이 이르거나 늦음) | 가장 작게 퍼짐 |
  | 누르지 못하고 놓친 Miss | 없음 (지금의 빨간 표시만) |
- **연마:** 결함 하나가 다 지워질 때마다 그 결함 자리에서 **반짝이는 이펙트**가 나온다. **흠집 크기 정도**이며 도넛형이 아니다. 모든 결함에 같은 크기.
- **색:** 단조 빛은 판정과 관계없이 **금색 계열로 통일**한다. 판정 정보는 기존 원 색(녹/노/빨)이 계속 맡는다. 연마 반짝임은 **은색 계열**이다.
- **방식: 파티클 시스템.** 이를 위해 Game 씬 `GameUICanvas`를 Screen Space - Overlay에서 **Screen Space - Camera**로 바꾼다. 파티클은 나중에 프리팹만 바꿔 교체할 수 있어야 한다.

## 비목표

- 가열·열처리 이펙트, 화면 흔들림, 판정 문구(“Perfect!” 글자) 표시.
- 판정 규칙·점수·난이도 변경. 효과음 변경.
- Title 씬 캔버스 변경.
- 최종 아트. 이펙트 텍스처·모양·색 세부는 임시값이며 최종 디자인은 **[미정]**이다.

## 하면 안 되는 것 (실패 조건)

- 이펙트가 다음 원·결함 입력을 가리거나 클릭을 막는다 (파티클은 레이캐스트 대상이 아니어야 한다).
- 캔버스 변경 뒤 기존 UI의 크기·위치·그리기 순서·클릭이 달라진다 (상점, 저장/불러오기, 설정, 제작 패널, 4개 미니게임, 결과 팝업, 튜토리얼 팝업, 화면 전환, 모루 클릭).
- 2D 조명이나 후처리(Bloom 등)가 UI 색을 바꾼다.
- 결과 팝업·튜토리얼 팝업 위로 이펙트가 그려진다.

## 방식 검토

| 방식 | 내용 | 장단점 | 결정 |
|---|---|---|---|
| A. UI 이미지 애니메이션 | 빛·별 이미지를 커지며 투명해지게 | 범위 작음, 새 패키지 없음. 파티클만큼 화려하지 않음. 나중에 파티클로 바꾸려면 캔버스 변경이 그때 필요 | 미채택 |
| **B. 파티클 + 캔버스 Camera 방식** | `GameUICanvas`를 Screen Space - Camera로 바꾸고 파티클을 UI 위에 그림 | 파티클 연출 자유, 이후 교체는 프리팹만. 게임 UI 전체 재확인 필요 | **채택 (사용자 선택)** |
| C. UI 파티클 외부 패키지 | 캔버스 그대로, 패키지로 UI 안에 파티클 | 외부 의존성, Unity 6 호환·빌드 확인 필요 | 미채택 |

## 현재 구조 (조사 결과)

- `GameUICanvas`: Screen Space - Overlay, sortingOrder 0, CanvasScaler ScaleWithScreenSize 1920×1080 match 0.5. Game 씬 유일한 루트 캔버스. 자식: 버튼들, InputBlocker, 패널들(Shop, SaveLoad, Crafting, Forge, Heat, HeatTreat, Polish, Settings), 화면 전환 3개, CraftResultPopup, TutorialPopup.
- `Main Camera`: Orthographic size 5, z -10, near 0.3. 배경 스프라이트는 모두 Sorting Layer `Default`, order -10 ~ -1. 정렬 레이어는 `Default` 하나.
- 모루 클릭은 `AnvilInteractable`(`IPointerClickHandler`, 카메라의 `Physics2DRaycaster`).
- `ForgeMinigameView`, `PolishMinigameView`의 클릭 좌표 변환은 이미 `eventData.pressEventCamera`를 쓰므로 Camera 방식에서도 그대로 동작해야 한다.
- `ForgeMinigame.Judged(CircleState)`는 놓친 Miss와 누른 Miss를 구분하지 않고, 어느 원인지도 넘기지 않는다. `Circle`에는 `Position`(미니게임 좌표)이 있다.
- `PolishMinigame.FlawCleared()`는 어느 결함인지 넘기지 않는다. `Flaw`에는 `Position`이 있다.
- 두 이벤트는 `CraftingSfx`가 듣는다 (효과음).
- `DefaultVolumeProfile`에 Bloom 컴포넌트가 있다. Camera 방식 캔버스는 카메라 후처리 대상이 될 수 있다.

## 설계

### 1. 판정 정보 보강 (Crafting, 로직)
- 단조: 원 판정 시 **어느 원인지와 눌렀는지**를 알 수 있게 한다. 예: `Circle`에 `Clicked`(눌러서 판정됐는가)를 추가하고 `Circle`을 넘기는 이벤트를 추가한다. 판정 규칙·점수는 바꾸지 않는다.
- 연마: 결함이 지워질 때 **어느 결함인지**(위치)를 알 수 있게 한다.
- 기존 이벤트(`Judged`, `FlawCleared`)와 `CraftingSfx`는 그대로 두는 것을 기본으로 한다. 시그니처를 바꾸는 쪽이 더 깔끔하면 `CraftingSfx`도 같이 고친다. (빌더 판단)
- 미니게임 모델은 계속 시각·오디오를 모른다.

### 2. 이펙트 재생 (UI)
- 이펙트는 **프리팹**(ParticleSystem)으로 둔다: 단조 빛 1개, 연마 반짝임 1개. 뷰는 프리팹 참조만 가진다.
- 단조는 **판정별 프리팹 3개**(`ForgeHitPerfect`/`ForgeHitGood`/`ForgeHitMiss`)를 쓴다. 한 프리팹을 통째로 줄이면 도넛의 구멍도 줄어 원을 가리므로 배율로 판정을 구분하지 않는다. 판정별 차이는 링이 퍼지는 정도·불꽃 수·밝기다.
- 도넛 조건: 링 텍스처(`SoftRing`)는 반지름 절반 안쪽이 완전 투명, 링 시작 크기는 기준 원 지름의 2배(구멍 = 원), 크기는 시작 뒤 줄어들지 않는다. 불꽃은 원 가장자리 바깥에서 생겨 바깥으로 나간다.
- 크기 배율은 **실제 원·흠집 지름 ÷ 기준 지름**(단조 160px, 연마 180px, 뷰의 Inspector 값)이다. 난이도 설정으로 원·흠집 크기가 바뀌어도 이펙트가 따라간다.
- 재생 위치는 원/결함의 미니게임 좌표를 각 뷰의 `playArea` 안 위치로 바꾼 곳.
- 재생 주체는 `ForgeMinigameView`/`PolishMinigameView`(좌표를 아는 곳) 또는 별도 작은 컴포넌트. 판정 이벤트 구독은 뷰의 Show/Hide에 맞춰 붙이고 뗀다.
- 이펙트는 짧게 끝난다 (0.3~0.5초 정도, 임시). 단계가 끝나 뷰를 숨길 때 남은 이펙트는 정리한다.
- 파티클 머티리얼은 **조명을 받지 않는(Unlit)** 것을 쓴다. 텍스처는 임시 (Unity 기본 파티클 텍스처 등).

### 3. 캔버스 전환 (Game 씬)
- `GameUICanvas`: Render Mode → Screen Space - Camera, Render Camera = `Main Camera`. Plane Distance는 카메라 near보다 크고 배경 스프라이트 앞에 오게 한다.
- CanvasScaler 설정은 그대로라 UI 크기·배치는 같아야 한다.
- 그리기 순서: 배경 < UI 패널 < **이펙트** < 결과 팝업·튜토리얼 팝업.
- **UI 정렬 레이어 (구현 후 추가):** 배경에는 순서 5인 화로 불꽃 파티클도 있어, 같은 Default 레이어에 캔버스(순서 0)를 두면 불꽃이 패널 위에 그려졌다. 그래서 정렬 레이어 `UI`를 Default 위에 추가했다. 월드(배경 스프라이트·화로 불꽃)는 `Default`, `UI` 레이어 안에서는 캔버스 0 < 이펙트 10 < 팝업 20(override sorting 하위 캔버스)이다.
- 2D 조명·후처리가 UI 색에 영향을 주지 않아야 한다. 영향이 있으면 막는다 (예: 카메라 후처리 설정 확인, UI·파티클이 Lit 셰이더를 쓰지 않게).

## 남은 결정 (빌더 몫)

- 판정 이벤트를 추가할지 바꿀지, 이펙트 재생 컴포넌트 위치.
- 판정별 퍼지는 정도(현재 링 바깥 지름 Perfect 512 / Good 432 / Miss 368px), 불꽃 수(16 / 10 / 5), 지속 시간, 파티클 모양, 금색·은색 정확한 값 (모두 임시).
- 그리기 순서를 맞추는 구체 방법, Plane Distance 값.

- 이펙트 최종 아트(텍스처·모양·색).

## 검증

- 컴파일 체크, Title/Game Missing Script 0, 콘솔 경고·오류 없음.
- 캔버스 전환 전후 UI 비교: 주요 RectTransform의 화면 위치(월드 코너 → 화면 좌표)가 같은지, 그리기 순서, 각 패널 열기/닫기 `onClick.Invoke()`.
- 모루 클릭 경로(`Physics2DRaycaster`)와 UI 클릭 차단(InputBlocker)이 그대로인지.
- 단조: Perfect/Good/누른 Miss/놓친 Miss 각각에서 맞는 프리팹이 나오는지(놓친 Miss는 없음), 링 구멍이 원 지름 이상이고 불꽃이 원 바깥에서 생기는지, 원 크기를 바꿔도 따라가는지. 연마: 결함 제거마다 1회, 빛 지름이 흠집 지름 정도인지.
- Camera 방식이면 `manage_camera screenshot`에 UI가 찍힐 수 있으므로 화면 확인을 시도한다. 실제 마우스 플레이, 빌드는 확인 못 할 수 있다 (보고).
- 씬 저장·커밋은 요청 시.
